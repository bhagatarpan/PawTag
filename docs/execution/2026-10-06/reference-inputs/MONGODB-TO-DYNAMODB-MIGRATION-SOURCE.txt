PawTag — MongoDB → DynamoDB Migration
Objective
Migrate PawTag's persistence layer from MongoDB/Mongoose to Amazon DynamoDB while preserving the existing application behaviour, API contracts, business rules, security boundaries, background-job semantics, commerce correctness, and client behaviour.

This is a database persistence migration, not a product rewrite.

The application currently uses:

Node.js / TypeScript

Express

Mongoose 7

MongoDB

packages/api for routes/services/jobs

apps/web

apps/admin

apps/mobile

The repository README and source code are the source of truth. Do not assume documentation is completely accurate.

NON-NEGOTIABLE RULES
1. Do not perform a big-bang rewrite
Do NOT delete packages/db, Mongoose models, or MongoDB configuration at the beginning.

Build the DynamoDB persistence layer alongside the existing MongoDB implementation.

Migration must proceed incrementally.

2. Preserve public API behaviour
Existing API routes, request payloads, response DTOs, status codes, authentication behaviour, authorization behaviour, and client expectations should remain unchanged unless a change is demonstrably required.

The frontend/mobile applications should NOT need to know that MongoDB was replaced.

Target architecture:

Applications
    ↓
API routes/controllers
    ↓
Domain/services
    ↓
Persistence interfaces/repositories
    ↓
DynamoDB

The database implementation should be replaceable without changing business logic.

3. Do not mechanically translate Mongoose into DynamoDB
Do NOT create:

Mongo model → DynamoDB table

for every model.

DynamoDB requires access-pattern-first data modelling.

For every existing model:

identify how the application reads/writes it;

identify query patterns;

identify ownership boundaries;

identify uniqueness requirements;

identify transaction requirements;

identify high-volume access patterns;

identify TTL/retention requirements;

identify relationships;

design DynamoDB keys/indexes around those access patterns.

4. Do not introduce a generic "Mongo compatibility" layer
Do not build a fake Mongoose-like abstraction over DynamoDB.

Do not reproduce:

.find()

.populate()

.aggregate()

.save()

arbitrary Mongo query semantics

inside a DynamoDB wrapper.

Create explicit repositories/domain persistence operations instead.

Examples:

getUserById()
getUserByEmail()
listUserPets()
getPetById()
getTagByPublicCode()
createOrder()
getOrderForCustomer()
listCustomerOrders()
claimBackgroundJob()
recordWebhookEvent()

Repository methods should describe business access patterns rather than database syntax.

PHASE 16 — BACKGROUND JOBS
Do not migrate the job scheduler until the DynamoDB concurrency model has been designed.

The existing MongoDB job locks must be replaced with DynamoDB conditional writes.

A job claim should behave conceptually like:

claim only if:
    no active lease
    OR lease expired

The operation must be atomic.

Do not use:

read lock
if available
write lock

because multiple workers can race.

Use conditional writes.

Jobs must remain idempotent.

PHASE 17 — TTL
Identify data that MongoDB currently expires automatically.

For each TTL collection determine:

business retention requirement;

whether DynamoDB TTL is appropriate;

whether deletion must be exact/timely;

whether compliance requires explicit deletion;

whether a scheduled cleanup job is still required.

Important:

DynamoDB TTL deletion is asynchronous.

Do not use DynamoDB TTL when the business rule requires deletion at an exact second.

PHASE 18 — PAGINATION
Replace Mongo pagination patterns carefully.

Do not translate:

into DynamoDB.

Prefer DynamoDB cursor pagination using:

ExclusiveStartKey

The API should continue exposing the application's existing pagination contract if possible.

If the API currently exposes page numbers, determine whether the service can internally maintain compatible behaviour without creating inefficient DynamoDB scans.

Never use table scans as a normal replacement for Mongo queries.

PHASE 19 — SEARCH
