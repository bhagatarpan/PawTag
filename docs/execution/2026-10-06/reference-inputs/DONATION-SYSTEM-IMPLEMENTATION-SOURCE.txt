 # 1\. Executive Summary

 PawTag should introduce a first-class donation capability that allows visitors, existing PawTag customers, and new supporters to financially support the PawTag mission.

 The donation system must not be treated as a simple Stripe payment button.

 It should be implemented as a complete financial domain integrated into the existing PawTag platform:

   ↓

   ↓

   ↓

   ↓
Generate donation receipt
   ↓
Generate PDF
   ↓
Email donor
   ↓

   ↓

   ↓

 The system should support:

- Stripe Customer records;

 The donation system must reuse PawTag's existing infrastructure wherever practical instead of introducing an entirely separate financial architecture.

 # 2\. Critical New Zealand Tax Requirement

 ## 2.1 Do not assume every donation is tax deductible

 PawTag must not describe a donation as "IRD claimable" merely because money was received.

 New Zealand donation tax credits depend on the recipient organisation being an approved donee organisation and the donation meeting the applicable requirements.

 IRD currently states that individuals can generally claim a donation tax credit for qualifying donations of $5 or more to an approved donee organisation, subject to the relevant rules and limits.  Inland Revenue+1

 Therefore the application must have an explicit organisation-level configuration:

```
DONATION_TAX_CREDIT_STATUS

NOT_ENABLED
PENDING_APPROVAL
APPROVED_DONEE
SUSPENDED
```

 The UI, receipts and email templates must derive their tax-credit language from this configuration.

 Never hard-code:

 > "Your donation is tax deductible."

 Instead use controlled copy such as:

 > "If PawTag is an approved donee organisation and your donation qualifies under New Zealand rules, you may be able to claim a donation tax credit."

 Once PawTag has confirmed approved donee status and the appropriate legal/accounting advice has been obtained, the copy can be changed accordingly.

 # 3\. IRD Receipt Requirements

 The donation receipt implementation must follow the current IRD requirements rather than inventing a PawTag-specific format.

 IRD currently states that donation receipts should contain information including:

 - donor's full name;
- donation amount;
- donation date or relevant tax year;
- a clear statement that the amount is a donation;
- organisation name;
- organisation IRD number;
- Charities Services registration number where applicable;
- official organisation identification/letterhead;
- authorised person's name/designation/signature;
- unique receipt number where applicable;
- `COPY` or `REPLACEMENT` designation when applicable.  Inland Revenue

 The system should therefore generate receipts containing the applicable fields.

 ## 3.1 Receipt data model

 A donation receipt should contain at least:

```
Receipt Number
Receipt Version
Receipt Status

Organisation:
    Legal Name
    Trading Name
    IRD Number
    Charities Registration Number
    Registered Address
    Official Logo
    Authorised Signatory
    Signatory Designation

Donor:
    Full Name
    Email
    Postal Address where required/collected

Donation:
    Donation ID
    Donation Date
    Donation Amount
    Currency
    Donation Type
    One-time / Recurring
    Payment Reference

Tax:
    Eligible For Donation Tax Credit
    Tax Credit Disclaimer / Classification
    Relevant Tax Year

Stripe:
    PaymentIntent ID
    Charge ID
    Customer ID
    Subscription ID where applicable

Document:
    PDF URL / storage key
    Online Receipt URL
    Issued At
    Generated At
```

 # 4\. Receipt vs Invoice

 ## Important architectural decision

 Do not treat a donation receipt as a normal commerce invoice.

 PawTag already has an invoice mechanism.

 Reuse the:

 - PDF generation infrastructure;
- document storage;
- email delivery;
- online document viewing;
- customer portal document components;
- admin document components;
- audit infrastructure.

 But introduce a distinct financial document type:

```
COMMERCE_INVOICE
CREDIT_NOTE
DONATION_RECEIPT
DONATION_RECEIPT_REPLACEMENT
```

 A donation is not a product sale.

 The donation receipt must therefore be its own domain document.

 # 5\. Product Philosophy

 The donation experience should feel like PawTag rather than a generic charity checkout.

 The design should communicate:

 > "You're helping us build a safer, faster way to reunite lost pets with their families."

 The experience should be:

 - warm;
- trustworthy;
- transparent;
- emotionally positive;
- fast;
- mobile-first;
- accessible;
- financially professional;
- consistent with the existing PawTag brand.

 Avoid:

 - guilt-driven messaging;
- aggressive donation popups;
- manipulative countdowns;
- fake urgency;
- confusing pricing;
- overly complicated forms.

 # 40\. Donation Refunds

 Donation refunds require special care.

 Admin may refund a donation if permitted.

 Flow:

```
Admin
 ↓
Refund donation
 ↓
Authorization
 ↓
Create Stripe refund
 ↓
Stripe confirms
 ↓
Persist refund
 ↓
Update donation
 ↓
Update receipt/tax status
 ↓
Notify donor
```

 If an eligible donation is refunded, the donor may need to account for the returned donation/tax credit under applicable IRD rules. IRD specifically notes that returned donations can require repayment of the related donation tax credit.  Inland Revenue

 Therefore the system should not leave an original eligible receipt looking unqualified after a full refund.

 Recommended approach:

```
Original receipt
      ↓
REFUNDED / VOIDED
      ↓
Refund notification
```

 Do not delete the original financial record.

 # 61\. DynamoDB Keys

 Do not blindly translate Mongo documents into DynamoDB.

 Example single-table strategy:

```
PK = CUSTOMER#<customerId>
SK = DONATION#<donationId>
```

 Payment:

```
PK = DONATION#<donationId>
SK = PAYMENT#<paymentId>
```

 Receipt:

```
PK = DONATION#<donationId>
SK = RECEIPT#<receiptId>
```

 Stripe lookup via GSI:

```
GSI1PK = STRIPE_PAYMENT_INTENT#<paymentIntentId>
GSI1SK = DONATION#<donationId>
```

 Recurring:

```
GSI2PK = STRIPE_SUBSCRIPTION#<subscriptionId>
GSI2SK = RECURRING_DONATION#<id>
```

 Actual key design must be finalized against the entire PawTag DynamoDB migration rather than designing a donation island independently.

 # 62\. DynamoDB Transactions

 # 95\. Donation vs Sponsorship

 # 216\. Final Recommendation

 PawTag should **not** build "a donation button".

```
ONE PAWTAG CUSTOMER
        │
        ├── Pets
        ├── Tags
        ├── Orders
        ├── Memberships
        └── Donations
                │
                ├── One-time
                ├── Recurring
                ├── Payments
                ├── Refunds
                └── Receipts

 A person can first encounter PawTag as:

Someone who found a lost pet

 then become:

```
A supporter
```

 then:

```
A donor
```

 then:

```
A PawTag customer
```

 then:

A pet owner with PawTag
```

 without ever needing a second identity system.

 That is the right foundation for PawTag.
